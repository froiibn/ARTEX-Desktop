# ARTEX Desktop 공개 전 최종 검토

후속 수정은 [수정 기록](public-release-remediation-20261014.md)을 참고한다. 이 문서는 아래 고정 소스·릴리스에 대한 과거 검토로 보존한다.

2026-10-14. 검토 대상은 `froiibn/ARTEX-Desktop`의 소스 commit `318fef3e82ffc3b31b23d35a05099927e1776aa9`와 기존 시험 릴리스 `v0.2.0-preview.1`이다. **현재 소스와 기존 릴리스를 함께 그대로 공개하는 것은 보류를 권고한다.** 소스의 빌드·기본 동작과 출처 보존은 확인했지만, 앱 고지와 공개할 배포 파일의 보완이 남아 있다. 이번 작업은 검토이며 저장소 공개 설정, 제품 코드, 기존 태그와 릴리스 파일을 변경하지 않았다.

## 확인한 항목

| 항목 | 결과와 확인 범위 |
| --- | --- |
| GitHub 상태 | 비공개 유지. 원격 기본 브랜치와 로컬 검토 commit 일치. 공개 대상 원격 ref는 `codex/rebuilt`와 기존 시험 태그 |
| 소스 빌드 | GitHub에서 별도 디렉터리에 새로 clone한 소스로 Windows `cargo build --offline --locked` 성공. 기존 Cargo 의존성 빌드 캐시를 재사용했으며 독립 toolchain의 완전한 무캐시 재빌드는 아님. 경고 없음 |
| 새 clone의 앱 동작 | 새로 빌드한 앱의 통합 자체 시험 성공. 별도 시험 작업 공간·프로필 사용, 실제 사용자 작업 공간·API 키 저장소 접근 및 실제 외부 대상 모의침투 없음 |
| 기존 전체 검증과의 대응 | 이전에 통과한 native 전체 회귀 결과의 184개 소스 해시가 현재 구현과 모두 일치. 이번 검토에서는 같은 전체 회귀를 중복 실행하지 않고 새 clone 빌드와 통합 자체 시험을 수행 |
| 원본 및 라이선스 | 루트·desktop LICENSE가 원본 로컬 LICENSE와 byte 일치. 원본 Git LICENSE와는 CRLF/LF 차이만 있고 본문 일치. 14개 Cargo manifest의 AGPL-3.0-only 선언 또는 상속 확인 |
| 원작자 및 참고 출처 | 원작자·수정·무보증 안내 보존. Norma와 Brevduva를 별도로 식별했으며 Brevduva LICENSE·NOTICE 원문 해시 일치. 상세 고지는 별도 라이선스 자료에 유지 |
| 소개 문서 | 한국어·영어·중국어 간체 README, 목적, 원작자 안내의 로컬 링크 51개 확인. 실행 명령, 현재 비공개 상태, Windows 배포 범위, 별도 외부 도구 필요 조건 유지 |
| 소스 이력의 비밀 정보 | 새 clone의 모든 브랜치·태그에서 도달 가능한 12개 commit·601개 blob 점검. 토큰·개인 키 패턴과 자격 증명 할당 후보 10건 검토 후 모두 단위시험의 고정 입력으로 분류. 실제 서비스 인증정보로 판정할 항목 발견 0건 |
| 업로드 제외 상태 | 현재 추적 파일 280개에 실행 파일·ZIP·DB·개인 키·실제 설정 파일 등 검사 대상 민감 파일명 없음. 모든 commit 이메일은 GitHub noreply. 텍스트에서 Windows 사용자 홈 경로 참조 없음. 14개 바이너리 blob의 알려진 인증정보 byte 패턴 발견 0건 |
| 기존 배포 무결성 | GitHub에 표시된 SHA-256과 보관된 ZIP·체크섬 파일 3개가 모두 일치. 두 ZIP의 내부 무결성 검사 성공. 소스 ZIP의 509개 파일이 해당 시험 태그의 Git blob과 모두 일치하며 누락·불일치 없음 |

비밀 정보 검사는 알려진 패턴과 확인된 후보의 코드 문맥을 검사한 결과다. 모든 인증정보 형식, 바이너리·이미지 내부의 임의 개인정보 또는 모든 소스의 권리 관계를 완전히 증명하는 검사는 아니다. 실제 자격 증명의 유효성을 외부 서비스에 조회하지 않았다.

## 공개 전에 처리할 항목

| 우선순위 | 확인된 문제 | 필요한 처리 |
| --- | --- | --- |
| 높음 | 원본 README의 온라인 테스트 금지 문구가 본 프로젝트의 허가된 모의침투 목적과 상충 | AGPL의 추가 제한 조항과 별도 약정 여부를 구분해 처리 방침과 근거를 확정하고 문서의 모호함 해소 |
| 높음 | native 정보 창에 원작자·무보증·AGPL 재배포권·라이선스/소스 접근 안내가 없음 | 기존 정보 메뉴에서 해당 안내에 접근할 수 있게 구현. 일반 화면에 상세 의존성 목록을 나열할 필요와 구분 |
| 높음 | 기존 Windows ZIP과 대응 소스 ZIP에 이후 복원한 Norma·Brevduva 고지 및 PSL 데이터의 MPL 자료가 없음 | 최종 소스 기준의 새 릴리스에 필요한 원문·NOTICE·정확한 대응 소스·빌드 안내·체크섬을 함께 제공 |
| 높음 | 기존 Windows ZIP의 selectors-0.31.0 경로는 다른 하위 구성 요소의 MIT/Apache 고지만 포함. GNU/MinGW 정적 런타임의 정확한 링크 출처와 기본 글꼴 고지 색인 보완도 미완료 | 실제 공개 빌드에 포함되는 구성 요소를 기준으로 MPL 원문·소스 안내, runtime exception·저작권, 글꼴 고지의 정확한 매핑 확인 |
| 범위 결정 | 현재 소스에서 제거한 웹/Tauri 코드는 과거 Git 이력과 기존 소스 ZIP에 남아 있음 | 기존 릴리스와 과거 소스의 공개 포함 여부를 결정하고 해당 출처·고지를 유지. 코드 제거를 과거 공개 범위 제거로 간주하지 않음 |

원본 사용 제한은 별도 허락이 반드시 필요하다고 단정할 항목은 아니다. [AGPL 7조](https://spdx.org/licenses/AGPL-3.0-only.html)는 해당 라이선스와 함께 붙은 추가 제한을 제거할 수 있는 경우를 규정하고, 10조는 추가 제한의 부과를 금지한다. 이 문구에 대한 적용 근거와 별도 약정의 존재 여부를 정리해야 하며, 방어적 목적이라는 설명만으로 정리가 완료되었다고 표시하지 않는다.

[AGPL 0·5(d)조](https://spdx.org/licenses/AGPL-3.0-only.html)는 대화형 UI의 적절한 법적 고지를 설명한다. 원본 로그인 UI에는 관련 안내가 있으므로 예외를 자동 적용하지 않는다. [Apache 2.0 4조](https://www.apache.org/licenses/LICENSE-2.0)의 원문·수정 표시·기존 NOTICE 보존은 상세 목록을 일반 README에 전시하는 것과 구분한다. MPL 소스·배포 조건은 [MPL 2.0 3조](https://www.mozilla.org/en-US/MPL/2.0/)를 따른다.

저장소 공개 전환 시 기존 릴리스도 공개 접근 대상이 되는 범위를 고려해야 한다. 소스만 공개하려면 기존 배포 파일의 공개 포함 여부부터 정리하고, 실행 파일까지 공개하려면 새 패키지 검토를 완료한다. 이번 검토에서는 기존 릴리스를 숨기거나 삭제하지 않았다.

## 배포 품질과 개인정보 측면의 추가 개선

- 기존 Windows 실행 파일에는 개발 PC 사용자 홈 아래 `.cargo`의 컴파일 경로 문자열이 남아 있다. 알려진 인증정보 byte 패턴은 발견되지 않았지만 사용자명과 빌드 환경이 드러날 수 있으므로 새 공개 빌드에 경로 치환을 적용하는 것이 좋다.
- 현재 제공 범위는 서명되지 않은 Windows x64 시험 ZIP이다. 설치 프로그램·자동 업데이트·macOS/Arch Linux 실기기 검증과 패키지는 미완료이며 세 언어 소개에도 이 범위를 유지한다.
- `desktop/ci/native-rust.yml`은 검증 템플릿이고 `.github/workflows`에 활성 workflow는 없다. GitHub 자동 빌드·검증·OS별 배포가 이미 작동한다고 설명하지 않는다.
- Brevduva 확인 commit은 라이선스 확인 기준이다. 구현 당시 실제 참고한 명세 버전과 문구·코드 사용 범위의 대조는 남아 있으며, 외부 Brevduva 라이브러리·SDK가 설치된 것으로 집계하지 않는다.

## 다음 공개 후보의 통과 조건

1. 원본 추가 사용 제한 처리 방침과 공개 목적 문구를 정리한다.
2. 앱 원작자·AGPL 안내를 보완하고 최종 제품 소스를 검증한다.
3. 공개할 최종 commit에서 필요한 고지와 대응 소스를 포함한 새 패키지를 만든다.
4. 새 패키지의 파일·소스 해시, 고지 매핑, 실행 시험을 확인한다.
5. 기존 릴리스·Git 이력의 공개 범위와 최종 후보를 제시한 뒤 공개 전환한다.
