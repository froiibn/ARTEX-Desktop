# SQLite 영속 저장 전환

## 변경 목적과 범위

2026-11-24 사용자 요청에 따라 자체 파일 저장 엔진을 앱에 번들한 SQLite로 대체한다. Rust 단일 프로세스, 객체 ID/관계, UI·도메인 명령, 승인·실행 감독은 유지한다. 별도의 DB 서버·Docker·SQLite 설치는 필요하지 않다. 이전의 객체 모델 선택을 자체 저장 엔진을 계속 유지해야 하는 요구로 해석하지 않는다.

## 저장 구조

- 작업공간과 공통 설정 저장소 모두 `Store` API를 사용하므로 동일한 SQLite 구현을 사용한다. 업무 DB는 각 저장소의 `store/workspace.sqlite3`다.
- `project.json`의 `format_version: 2`, `storage: sqlite-v1`이 새 형식의 식별자다. 이전 앱은 v2를 거부하며 이전 저널에 새 작업을 기록하지 않는다.
- `objects`: 객체별 행. 컬렉션/ID 복합 기본 키, 버전, 저장 순서, 헤더와 타입 검증된 JSON 데이터. 전체 작업공간을 단일 JSON Blob으로 저장하지 않는다.
- `relationships`: 모델에서 유도한 관계의 양 끝 객체를 SQLite 지연 외래 키로 보호한다. 원래 데이터 키가 헤더 ID와 다른 관계도 실제 대상 객체로 해석해 기록한다.
- `tombstones`: 삭제된 ID의 재사용 방지와 이전 정보.
- `metadata`: 저장소 ID, 이름, 확정 순서, 체크포인트 세대.
- `checkpoints`: SQLite 체크포인트 메타데이터와 그 SHA-256. 기존 API의 `manifest_sha256`은 이 실제 저장된 메타데이터의 해시이며 DB 파일 전체의 해시가 아니다.
- `legacy_blob_roots`: 이전 시점의 증거 파일을 보존하는 참조. 기존 형식의 백업을 새 DB의 정리 작업이 손상시키지 않는다.
- 객체의 task/run/exploration 필드와 관계 역방향에 SQL 인덱스를 둔다. 현재 UI·도메인의 불변 조회 세대와 메모리 조회 인덱스도 유지한다. UI 조회를 전부 SQL로 전환했다고 주장하지 않는다.

첨부·대형 증거는 기존 SHA-256 파일 저장을 유지한다. 외부 도구의 스크립트·작업 파일도 실제 파일이어야 한다. API 키는 SQLite 평문으로 옮기지 않으며 기존 OS 비밀 저장소의 참조를 유지한다.

## 트랜잭션과 검증

WAL과 `synchronous=FULL`, 외래 키 검사를 사용한다. 앱의 단일 writer와 작업공간 OS 잠금을 유지한다. 한 명령의 객체 변경·관계·삭제 표시·명령 영수증·저장 순서는 하나의 SQLite 트랜잭션으로 확정한다. SQLite에서도 버전 CAS를 재확인하며 명령 ID 재실행은 기존 영수증을 반환한다.

복원 시 전체 타입·관계·업무 무결성과 참조 Blob을 확인한다. 이미 검증한 세대에서의 변경은 수정된 레코드, 영향받은 관계, 해당 컬렉션의 유일성, 기존 업무 의미를 검증한다. 매 변경마다 모든 과거 본문을 다시 해시하지 않는다. SQLite 테이블 제약만으로 도메인의 모든 권한·업무 규칙을 대체하지 않는다.

Rust 메모리 Snapshot의 복사와 UI 세대별 인덱스 구성은 호환 경계로 남는다. 이 전환만으로 모든 메모리·UI·스트리밍 병목이 해소됐다고 해석하지 않는다.

## 기존 작업공간 이전

1. 기존 형식은 읽기 전용으로 체크포인트·저널 체인·본문을 검증한다. 잘린 꼬리를 자르거나 기존 파일을 다시 저장하지 않는다.
2. 정상적인 쓰기 열기에서만 임시 SQLite를 만들고 객체·헤더·버전·명령 영수증·삭제 표시·관계를 한 트랜잭션으로 이전한다.
3. SQLite를 다시 열어 모든 레코드와 삭제 정보가 동일한지 비교한다. 빈 컬렉션의 명시적 표현 차이는 데이터 손실로 계산하지 않는다.
4. DB를 설치하고 원래 `project.json`을 `backups/pre-sqlite-project.json`에 보존한다. 마지막으로 동기화한 v2 설명 파일을 원자적으로 교체한다.
5. 설명 파일 교체 전에 종료됐으면, 설치된 DB와 기존 저장 세대가 동일한 경우에만 이전을 재개한다. 다르면 `RECOVERY_REQUIRED`로 중단하며 덮어쓰지 않는다.

기존 저널·스냅샷·증거 파일은 자동으로 삭제하지 않는다. 손상된 기존 저장소는 복구가 필요한 읽기 전용 상태로 남고 자동 이전하지 않는다. 읽기 전용으로 연 기존 공간도 이전하지 않는다. 새 백업을 기존 앱에서 열 수 있다고 보장하지 않는다.

## 읽기 전용·복구·정리

정상 종료된 SQLite는 원본에 sidecar를 만들지 않는 immutable 읽기로 연다. 강제 종료 후 WAL이 남아 있으면 작업공간 잠금 아래 DB/WAL을 임시 디렉터리에 복사하고 SQLite 자체 복구를 그 복사본에서 수행한다. 원본의 WAL·SHM·본문을 수정하지 않는다.

복구 내보내기는 새 SQLite 작업공간에 검증된 현재 데이터와 증거를 저장한 뒤 재열기 검사까지 통과해야 게시한다. 기존 형식의 부분 복구도 같은 새 형식으로 내보낸다. DB 페이지가 손상돼 검증된 스냅샷을 얻을 수 없는 경우에는 열기를 실패시키며 빈 공간이나 복구 성공으로 표시하지 않는다.

증거 정리는 현재 세대, 살아 있는 조회 pin, 이전 파일 보존 루트, 최소 24시간 유예를 반영한다. SQLite WAL의 삭제·복구·체크포인트는 SQLite에 맡기며 앱이 WAL 파일을 임의로 지우지 않는다. DB와 WAL을 함께 고려해야 하므로 실행 중 DB 파일 하나만 복사하는 백업 방식은 사용하지 않는다.

## 의존성과 지원 범위

`rusqlite 0.40.2`의 bundled SQLite를 사용한다. 기존 importer도 같은 버전을 사용해 서로 다른 SQLite 네이티브 라이브러리의 중복 링크를 피한다. 해당 번들의 SQLite 3.53.2는 [WAL-reset 수정](https://www.sqlite.org/wal.html#the_wal_reset_bug)이 포함된 버전이다.

Windows 격리 프로세스 검증과 macOS·Arch Linux 실기기 검증은 별도다. WAL의 로컬 파일시스템 전제를 따른다. NAS·네트워크 공유·클라우드 동기화 중인 DB의 동시 사용은 이번 검증 범위에 포함하지 않는다.

## 수락 검증

- SQLite 생성·명령 수락·CAS·중복 방지·저장·읽기 전용 재열기.
- 기존 파일 이전 시 ID·헤더·본문·영수증·삭제 표시와 이전 원본 파일 보존.
- 이전 중단 후 재개와 서로 다른 DB가 남은 경우의 차단.
- 실제 격리 프로세스 강제 종료 후 확정 트랜잭션 보존·미확정 트랜잭션 제거·WAL 복구.
- 외래 키, 삭제 ID 재사용, 체크포인트 해시, pin과 증거 정리.
- 모델·에이전트 공통 설정, 작업·대화·사이트 보고서, 서비스 수명주기와 네이티브 UI의 회귀.

실행 결과와 남은 제약은 최신 `desktop/native/STATUS.md`의 SQLite 전환 기록에서 구분한다. 전체 원본 동등성 수락으로 자동 승격하지 않는다.


### 2026-11-24 실행 결과

저장소 42건, 최종 앱 서비스 45건, 네이티브 UI 153건이 통과했다. 표준 Windows 실행 파일의 통합 자체 검사도 실제 SQLite 생성과 로컬 공급자 4회 요청을 포함해 통과했다. 원본 분석 이력의 격리 복사본 9,962개 레코드를 ID·헤더·내용 변경 없이 이전했고 기존 원본 파일을 보존했다. 과거 실패 로그와 동시 시험의 시간 초과는 성공으로 집계하지 않는다. 최종 소스/실행 파일 해시와 상세 제약은 [현재 상태](../desktop/native/STATUS.md)를 참고한다.

대형 Body 및 기존 공통 설정 catalog가 참조하는 Blob은 기존 참조 형식과 파일을 보존한다. SQLite 메타데이터와 증거 파일을 함께 백업해야 하며 DB 파일 하나가 전체 작업공간을 포함한다고 가정하지 않는다.
