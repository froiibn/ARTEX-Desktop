# ARTEX Desktop 종합 최종 점검 보고서

기준일: 2026년 10월 20일 · 대상: 현재 로컬 개발 소스와 보존된 검증 결과

**현재 상태는 Windows에서 핵심 흐름을 시험할 수 있는 개발 버전이며, 원본 기능 전체의 동등성과 최종 안정판 수락은 완료되지 않았다.** 최근 UI 시험 145건과 현재 실행 파일의 통합 자체 시험은 통과했다. 그러나 원본 대응 검증표의 화면 명령·도구 339행 가운데 연결된 종단 간 근거가 있는 행은 제한된 시나리오 10행이고, 329행은 전체 경로 수락이 남아 있다. 이 숫자는 구현률이나 결함 수를 뜻하지 않는다.

이 보고서는 프로젝트 목적과 구현 구조, 확인한 범위, 수정 결과, 남은 문제, 개선 순서와 안정판 완료 조건을 한곳에 모은다. 상세 이력은 유지하되 현재 판단은 아래 내용을 따른다. 이번 작업은 코드·검증 기록을 종합하는 문서 작업이며 제품 코드 수정, 새 제품 시험, 화면 자동 조작, 커밋·푸시·릴리스는 수행하지 않았다.

## 프로젝트 목적과 현재 구조

원본 ARTEX는 LLM 기반 에이전트와 보안 도구로 작업·자산·취약점·증거를 관리하는 솔루션이다. Desktop 재구축의 목적은 Docker, 웹 서버, PostgreSQL 등을 직접 구성하는 부담을 줄여 비전공자도 자신이 개발·운영하거나 테스트 권한을 가진 서비스의 취약점을 분석하고 대응하도록 돕는 것이다.

현재 앱의 기본 실행에 Go, Node/npm, PostgreSQL 서버, Docker, WebView는 필요하지 않다. 개발자가 소스에서 빌드할 때 사용하는 Python 스크립트와 Rust 도구 체인은 일반 사용자의 기본 실행 조건과 구분한다. Nmap·Python 스크립트·셸·외부 MCP 서버 자체를 모두 Rust로 다시 구현한 것은 아니다. 해당 기능은 앱이 감독하는 외부 도구 또는 외부 서비스로 남는다.

| 계층 | 구현과 역할 | 코드 기준 |
|---|---|---|
| 네이티브 화면 | Rust, eframe/egui. 작업 공간·작업·대화·결과·설정 표시 | [native/Cargo.toml](../desktop/native/Cargo.toml), [app.rs](../desktop/native/src/app.rs) |
| 앱 서비스 | 같은 프로세스 안의 Rust 서비스와 형식이 정해진 요청 채널. 작업 공간·실행 수명·저장 요청 조율 | [native-core](../desktop/native-core/src/lib.rs) |
| 업무와 실행 조정 | 작업·대화·회사·자산·발견 사항·승인·LLM 실행·결과 계약 | [domain](../desktop/crates/domain/src/lib.rs), [RPC facade](../desktop/crates/rpc/src/facade.rs) |
| 로컬 저장 | 객체 그래프, ID 참조, 버전 비교 후 갱신(CAS), 저널·체크포인트·SHA 기반 본문 파일 | [store](../desktop/crates/store/src/lib.rs) |
| 에이전트 정보 공유 | 공유 객체와 영속 메시지·전달 상태. 요청/응답·수신 확인·업무 완료를 구분 | [agent](../desktop/crates/agent/src/lib.rs), [메시지 계약](../desktop/contracts/agent-message.v1.schema.json) |
| 모델과 도구 | 공급자별 요청·JSON/SSE 응답 처리, 도구 제공·권한 판단·외부 프로세스 감독 | [runtime](../desktop/crates/runtime/src/lib.rs), [host](../desktop/crates/host/src/lib.rs) |

Brevduva는 **프로토콜 구조를 참고한 출처**다. 현재 내부 계약은 `artex-agent/1.0`이며 Brevduva 서버·수신기·SDK를 설치하거나 연결하는 구성이 아니다. 참고 범위와 Apache 원문·NOTICE는 [구조 참고 문서](brevduva-structure-reference.md)에 있다.

## 무엇을 어떻게 검증했는가

종단 간 검증은 **실제 입력 → 명령 접수와 권한 확인 → 실행 → 저장 → 같은 작업 공간 재열기 → 조회와 화면 표시**가 연결돼야 한다. 내부 함수 시험, 계약 등록, 빈 결과 반환, 화면 렌더링만으로 전체 업무가 통과한 것으로 계산하지 않는다.

V19의 최적화 실행 시험 전체 시간은 읽기 전용 11.291초, 일반 복사본 37.169초였다. 화면 순회와 종료까지 포함하므로 순수 열기 속도나 전후 개선 배수로 해석하지 않는다.

사용자 요청으로 Computer Use 조작을 중단한 이후 다시 시작하지 않았다. 따라서 최신 UI 145개 통과와 과거 실제 창 캡처를 합쳐 최신 화면의 육안 확인까지 끝났다고 표현하지 않는다. 최근 시험은 실제 사용자 API 키나 운영 사이트를 호출하지 않고 격리된 작업 공간·로컬 공급자를 사용했다.

### 개별 검증표의 현재 집계

| 대상 | 전체 | 출처 대응 | 대응 확인 필요 | 미검증 | 부분 경로 통과 | E2E 통과 | 변경점 통과 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 원본 HTTP 출처 행 | 261 | 259 | 2 | 해당 없음 | 해당 없음 | 해당 없음 | 해당 없음 |
| 화면 명령 행 | 258 | 해당 없음 | 해당 없음 | 132 | 121 | 4 | 1 |
| 도구 행 | 81 | 해당 없음 | 해당 없음 | 0 | 76 | 5 | 0 |

세 목록은 같은 업무를 서로 다른 경계에서 가리키므로 600개 독립 기능으로 합산하지 않는다. HTTP 행은 출처 목록이다. 실행 수락 대상 339행 중 **9행의 E2E 통과와 1행의 변경점 통과를 합친 10행**에 제한된 연결 시나리오 근거가 있다. 132행은 미검증, 197행은 부분 경로 통과여서 전체 경로 수락이 남는다.

현재 해당 10행은 작업 생성, 보관 작업 복원, LLM 프로필 삭제, 대화 생성·전송, `Read`, `WebFetch`, `shell_list`, `shell_open`, `shell_read`다. 각 행의 성공은 등록된 시험 시나리오 범위에 한정된다. 예를 들어 대화 생성 행의 수락이 사용자 최초 이름 오류의 직접 원인 확정을 뜻하지 않는다.

상세 목록은 [검증표 설명](e2e-feature-verification.md), [JSON](e2e-feature-matrix.v1.json), [CSV](e2e-feature-matrix.v1.csv)를 따른다. JSON 안의 `last_verification`은 10월 17일의 9행 수락 집계이며, 위 표는 이후 수정된 현재 `rows`와 검사기 결과로 계산했다.

## 의도적으로 바꾼 사항

다음은 사용자 지시 또는 확정 명세에 따른 유지 대상이다. 원본과 다르다는 이유로 결함으로 되돌리지 않는다. 변경 과정에서 생긴 명령 실패·자료 손실은 별도로 다룬다.

## 라이선스와 공개 상태

현재 소스와 manifest의 프로젝트 라이선스는 **AGPL-3.0-only**다. 원작자 Autumn-27, 수정 출처, Norma와 Brevduva 구조 참고, 글꼴·런타임·기타 해당 구성요소의 원문과 고지를 보존한다. 일반 소개에는 원작자 중심으로 설명하고 상세 배포 고지는 별도 자료로 유지하는 구조다.

과거 라이선스 감사에서 발견한 원문·NOTICE·앱 고지·대응 소스·배포 검증 문제는 [공개 전 수정 결과](public-release-remediation-result-20261014.md)에 후속 처리를 기록했다. 원본 README의 추가 사용 제한은 [처리 방침](license-policy.md)을 따른다. 초기 감사 문서의 문제 목록을 후속 수정 여부와 무관하게 현재 미해결 목록으로 복사하지 않는다.

Cargo 잠금 파일의 전체 항목 수는 작성자가 직접 가져온 프로젝트 수나 바이너리에 모두 포함되는 구성요소 수와 같지 않다. 현재 개발 출력은 원작자 고지와 라이선스 사본을 포함하지만 정식 배포에 필요한 전체 고지·대응 소스 조립을 대체하지 않는다. 외부 Nmap/Python 등을 향후 함께 번들한다면 해당 배포 입력의 조건을 다시 확인해야 한다. 이 보고서는 현재의 법률적 적합성을 새로 보증하는 문서가 아니다.

공개 저장소와 `preview.4`에 관한 내용은 로컬 README·보존된 배포 기록의 상태 설명이다. 이번 보고서 작성에서 GitHub의 최신 CI·태그·릴리스·자산 해시를 새로 조회하지 않았다. 과거 CI 실패·성공은 기록된 commit/job에만 적용하며 현재 수정본 CI 성공으로 바꾸어 표현하지 않는다.

## 개선 순서와 안정판 완료 조건

### 먼저 완성할 사용자 흐름

| 순서 | 연결할 흐름 | 반드시 확인할 결과 |

수정은 [작업 규칙](../AGENTS.md)에 따라 재현 가능한 가장 작은 원인에 한정한다. 결함마다 실패 사례를 먼저 고정하고, 실제 공개 명령과 native 입력을 연결한 뒤 정상·오류·취소·저장·재열기를 확인한다. 소스 변경이 있으면 영향 범위를 다시 정해 회귀를 수행하고, 통과한 이전 결과를 새 소스의 결과로 덮어쓰지 않는다.

### 안정판 수락 조건

- 유지 대상 339행의 연결 경로를 수락하고, 별도 legacy 참조 12행과 수동 API 2개의 대응·실행·범위를 해결한다. 명시적 변경은 승인된 새 동작과 `변경점 통과` 근거로 남긴다.
- 현재 고정 소스로 전체 회귀·계약·프롬프트·최적화 빌드·동일 실행 파일 자체 시험을 통과한다. 사용자 보고의 미확정 증상은 원인 또는 제한된 재현 범위를 명시한다.
- 최신 화면에서 실제 입력·최소 창·테마·한국어 입력·상태 표시·중지/삭제·공간 전환·정상 종료를 확인한다. 화면 조작 중단 지시는 별도 재개 전까지 유지한다.
- 실제 대상 OS별 자료·키 저장·절전·충돌 복구·외부 프로세스 정리를 수락한다. Windows만 먼저 안정판으로 제공한다면 Mac/Linux는 별도 미수락 대상으로 명시한다.
- 수정 소스의 commit/태그, 빌드 입력, 실행 파일, 대응 소스와 고지, 패키지 해시·재추출 결과를 고정한다. 최신 원격 CI와 게시된 파일까지 같은 배포 대상을 가리켜야 한다.

등록 개수, 전체 단위 시험 수, 23개 화면 렌더링 중 어느 하나만으로 이 조건을 대신하지 않는다. 코드 서명·설치 프로그램·자동 업데이트는 현재 구현 완료 범위가 아니며, 도입 시 해당 플랫폼의 배포 작업으로 별도 검증한다.
